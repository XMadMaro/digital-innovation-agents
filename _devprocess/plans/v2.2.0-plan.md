# v2.2.0 Plan: Workflow Improvements from LinkedIn Feedback

## Context

The LinkedIn article "PULSE: A Post-Scrum Manifesto for AI-Native Teams"
drew five substantial critiques. Collectively they expose the same
pattern: the V-Model Workflow has a forward bias. It describes how
information flows forward (BA to RE to Architecture to Code). It
describes less how information flows back, how parallel agents
coordinate, and whether the system is pulsing in the right direction.

This release addresses six improvements plus one supply-chain item
from Issue #9.

## Scope

### FEATURE-001-001: Signal Layer (Comment #3: Observability)

**Problem.** No metrics, no observability at workflow level. Teams
cannot tell if the system is moving in the right direction or just
moving fast.

**Approach.** New artifact `_devprocess/context/40_metrics.md` written
by the phase skills during their own handoffs. Signals stay lightweight
and derivable: cycle time per FEATURE (from commit Refs), drift count
between plan-context.md and real code (captured during coding
reconciliation), BA hypothesis validation status per hypothesis, phase
transition counts. Also a new `METRICS-TEMPLATE.md` in the
v-model-workflow skill.

**Skills touched.** v-model-workflow (orchestrator writes + template),
coding (drift count during reconciliation), business-analyse (hypothesis
status), project-conventions (document the new file in directory-structure.md).

### FEATURE-001-002: Dialog Handoffs (Comment #6: Waterfall in cycles)

**Problem.** Handoff documents are one-way. architect-handoff.md from
RE to Architect, plan-context.md from Architect to Coder. Receiver has
no formal way back. A critique that the handoff docs feel like waterfall
throw-over-the-fence.

**Approach.** Add a `## Dialog` section to architect-handoff.md and
plan-context.md templates. Receivers write questions or challenges
there. The dialog section is NOT a blocker. When the originating skill
runs again, it checks for new dialog entries and triggers an
AskUserQuestion: "The Architect had N questions on your handoff.
Address now, defer to next iteration, or ignore?". Answers append
to the dialog, creating a trail. Both agent-agent and agent-human
dialog paths are supported.

**Skills touched.** requirements-engineering (template + dialog check
trigger), architecture (template + dialog check trigger on run),
coding (dialog check on run), v-model-workflow (document the pattern).

**Design rule (user feedback).** MUST NOT become an annoying blocker.
MUST trigger dialog (agent-agent, agent-human).

### FEATURE-001-003: Cross-Phase Feedback Triggers (Comment #6)

**Problem.** The mid-course bug trigger in `/coding` handles code bugs
only. Design-level or requirements-level discoveries during coding have
no formal route. Design issues get fixed silently. Requirements gaps
get worked around.

**Approach.** Add two parallel triggers on the bug-trigger pattern:
1. Mid-course Design Discovery in `/coding` (ADR amendment path).
2. Mid-course Requirements Discovery in `/architecture` (FEATURE-spec
   update path).
Same 6-step template as the bug trigger (STOP, triage, root-cause,
backlog-entry, commit with Refs, Final sync). Together with the existing
bug trigger, the V becomes a decision graph.

**Skills touched.** coding (Design Discovery trigger), architecture
(Requirements Discovery trigger), v-model-workflow (document all three
triggers as the cross-phase feedback mechanism).

### FEATURE-001-004: BA as Living Document after Release

**Problem.** The BA freezes at "Validated" status. Real user data from
shipped features does not flow back into the hypotheses. Every
Critical Hypothesis stays as "Validated" (by reasoning) forever,
never "Confirmed by usage" or "Contradicted by usage".

**Approach.** New optional Phase 8 in the BA: Post-Release Review.
Triggered either manually or by a post-release handoff from `/coding`.
Reads BA Section 7.3 (Critical Hypotheses), compares each hypothesis
against the observed signals (from 40_metrics.md) or user feedback,
and promotes status from `Validated` to one of:
- `Confirmed by usage` (evidence cited)
- `Contradicted by usage` (evidence cited, triggers new backlog entry)
- `Inconclusive` (not enough data yet)

**Skills touched.** business-analyse (new Phase 8), coding (post-release
handoff writes a note to trigger /business-analyse review).

### FEATURE-001-005: Concurrent-Agent Coordination (Comment #4)

**Problem.** Multiple human-agent pairs working in parallel conflict on
backlog writes. The backlog is the only synchronization point and it
has no ownership or locking.

**Approach.** Add `Owner: {pair-id}` and `Claimed: {timestamp}` fields
to backlog rows. Phase skills claim their backlog items on start
("Owner: sebastian-claude-opus-4.7") and release on phase end. Claim
conflict (two pairs try to claim the same row) triggers AskUserQuestion
that routes to the current owner: "pair-X wants to work on BL-017
which you claimed. Release now, split the item, or defer?". If no
Owner is set, any pair may claim.

**Skills touched.** requirements-engineering (backlog template fields),
v-model-workflow (claim and release protocol at phase start and end),
project-conventions (document the protocol).

### FEATURE-001-006: Short-Loop Iteration explicit (Comment #6)

**Problem.** The V-Model looks linear. The diagram suggests a single
forward walk. Reality is iterative. Requirements discovery during
coding is the rule, not the exception.

**Approach.** Pure documentation update. No new skills.
1. v-model-workflow SKILL.md: explicit "V is a decision graph, not a
   path" section.
2. Each phase-skill: short "When to return to the previous phase"
   section listing triggers.
3. Landing-page SVG (docs/index.md): add thin return arrows between
   adjacent phases.
4. Doc concepts/v-model.md: paragraph on iterative usage.

**Skills touched.** v-model-workflow, each phase-skill (BA, RE, Arch,
Coding, Testing, Security Audit), concepts/v-model.md, landing SVG.

### FEATURE-002-001: SHA-pin GitHub Actions (Issue #9 Gap 1)

**Problem.** Today `actions/checkout@v4` resolves to whatever `v4`
currently points at. A compromised PAT or tag move could silently
replace the commit. Trust chain relies on GitHub not lying about tags.

**Approach.** Pin every third-party action in
`.github/workflows/deploy-docs.yml` to a 40-char SHA with the
human-readable version as a trailing comment. Existing actions to
pin: `actions/checkout@v4`, `actions/setup-node@v4`,
`actions/configure-pages@v5`, `actions/upload-pages-artifact@v3`,
`actions/deploy-pages@v4`.

Configure Dependabot to continue bumping both SHA and comment together.

**Files touched.** `.github/workflows/deploy-docs.yml`,
`.github/dependabot.yml` (new, or extend existing).

## Sequencing

Priority order for implementation:

1. FEATURE-002-001: SHA-pin workflows (smallest, highest-signal
   security posture, unblocks Gap 2 and Gap 3 in later releases)
2. FEATURE-001-006: Short-Loop Iteration explicit (pure documentation,
   low risk, big clarity win)
3. FEATURE-001-001: Signal Layer (new artifact, standalone)
4. FEATURE-001-003: Cross-Phase Feedback Triggers (extends existing
   mid-course bug trigger pattern)
5. FEATURE-001-002: Dialog Handoffs (depends on understanding signal
   layer and cross-phase triggers)
6. FEATURE-001-004: BA as Living Document (depends on signal layer)
7. FEATURE-001-005: Concurrent-Agent Coordination (most complex,
   changes the backlog schema, touches every phase-skill)

## Not in scope (for v2.2.0)

- UX/Design as optional phase. Waiting for Claude Design availability.
- Issue #9 Gap 2: cosign signing. Needs key management decision first.
- Issue #9 Gap 3: SHA256SUMS publishing. Depends on Gap 2 for the
  release-process change to land together.

## Acceptance

Each FEATURE is complete when:
- All named skills are updated
- The CHANGELOG has a v2.2.0 entry describing the addition
- The templates (if changed) pass the em-dash and AI-vocab scan
- A short demo in v-model-workflow documentation shows the pattern
